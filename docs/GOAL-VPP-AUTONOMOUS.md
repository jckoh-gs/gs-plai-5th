## 1. 최종 목표

외부 VPP 예측 및 입찰·제어 시스템을 실제 발전설비 없이 개발·검증할 수 있는 SCADA·RTU 통합 에뮬레이터를 완성한다. PRD를 출발점으로 사용하되 작업 중 발견한 문제와 유용한 개선 아이디어를 검토하고, PRD와 제품을 함께 버전 관리하며 발전시킨다.

핵심 데이터 흐름은 **SCADA 전체 데이터 → RTU → MQTT → VPP 시스템**, 핵심 제어 흐름은 **VPP 목표값 → MQTT → RTU 검증·변환 → SCADA 제어 → 발전기 출력 피드백 → VPP 결과**다. 화면만 구현한 상태가 아니라 실제 로컬 MQTT 왕복과 출력 결과로 동작을 증명해야 한다.

메인 개발, 독립 기능 개발, PRD·아이디어, 보안·취약점, 이슈·해결 기록 담당이 역할을 나눠 병행한다. AI가 허용된 범위에서 설계·구현·검증·우선순위를 결정한다. 정해진 시간 전에 필수 목표를 달성하면 핵심 목적에 도움이 되는 추가 목표를 제안·기록·채택하여 이어간다. 마지막 30분은 기능을 동결하고 검증된 버전의 시연 영상 제작 → 발표자료 PPT 작성 → 최종 검증·인도 순서로 사용한다.

## 2. 문서 관계와 적용 우선순위

- **사용자의 최신 명시적 지시:** 시작·중단·재개, 범위·마감 변경의 최우선 기준.
- **이 목표 문서:** 결과, 협업, 자율성, 시간, 검증·복원·인도의 운영 기준.
- **기준 PRD:** 기능·화면·계산식·데이터 계약·인수 조건.
- **실행 시 작성하는 작업 지시서와 변경 기록:** 담당별 범위·의존성·수락 조건·실행 증거.

PRD의 운영 조항과 이 문서가 충돌하면 최신 사용자 지시와 이 문서의 실행 승인·상대시간 정책을 따른다. 특히 기존 PRD/운영 기록에 들어 있는 2026-09-21~22의 고정 시각은 취소된 과거 기록이며 이번 실행 시각이 아니다.

PRD를 변경해 어려운 필수 요구사항을 삭제하거나 수락 조건을 낮춘 뒤 성공으로 처리하지 않는다. 추가 아이디어는 기존 핵심 목표를 유지하며 변경 이유·영향·수락 조건을 기록한다. 중대한 목적 변경은 사용자에게 확인해야 한다.

## 3. 실행 승인과 기준선

### 3.1 시작 조건

사용자가 “이 목표 문서에 따라 지금 시작하세요”처럼 명시적으로 실행을 요청해야 한다. “문서를 작성해 주세요”, “계획을 검토해 주세요”, “이 방식이 가능합니까”는 시작 지시가 아니다. 시작 요청이 있기 전에는 개발용 목표 생성·재개, 모니터 세션 실행, 자동화 활성화, 코드 변경 또는 시험 실행을 하지 않는다.

### 3.2 시작할 때 기록할 항목

새 실행 ID, 실제 시작 UTC/KST, 동결 시각, 마감 시각, 기준 PRD 버전과 해시, 출발 Git 커밋, 작업본 변경 목록, DB 백업 위치, 역할별 세션 ID, 모델, 실행 환경과 검증 명령을 기록한다. 기본 모델은 요청한 Codex Astra이며 사용 불가 시 임의로 바꿔 동일 조건이라고 주장하지 않는다. 별도 토큰 상한을 임의로 설정하지 않되 계정·환경 제한을 우회하지 않는다.

이번 실행이 새 구현인지 기존 구현의 개선인지 시작 지시에서 정한 범위를 따른다. 명시되지 않으면 현재 프로젝트의 기존 구현과 미완성 변경을 보존하며 PRD를 기준으로 보완한다. 새 구현을 지시받으면 별도 폴더/브랜치에서 시작하고 기존 결과물을 덮어쓰지 않는다.

### 3.3 현재 작업본에 관한 인수 주의

문서 작성 시점에 `stable-v2.0.1`(425b985835c1a82c88db7c56e6643cd078409ab0) 및 미커밋 보안·MQTT 보고서 작업이 존재한다. 이 식별자는 과거 상태의 참고값이며 다음 실행의 기준선으로 자동 확정하지 않는다. 실제 시작 시 다시 검사하고 미완성 변경을 별도 보존한 뒤 출발점을 기록한다. 과거 검증은 현재 작업본의 검증을 대신하지 않는다.

### 3.4 저장소와 배포 대상

- Git 저장소: `git@github.com:jckoh-gs/gs-plai-5th.git` ([GitHub](https://github.com/jckoh-gs/gs-plai-5th)).
- 원격 배포 플랫폼: k3s, kubectl context는 `charles-k3s`, namespace는 `gs-plai-5h`.
- namespace는 사용자가 확정한 배포 대상이며 존재·생성·접근 권한은 아직 검증하지 않았다.
- 확인된 연결: Git `ls-remote` 읽기 성공(종료0, ref없음), k3s API `/version` 접근 성공.
- 서버 응답: `v1.33.4+k3s1`, API 서버 플랫폼 `linux/amd64`. 전체 노드 아키텍처 확인 결과는 아니다.
- 계정: 사용자가 admin 계정이라고 제공했다. 실제 push·RBAC·배포 권한 검증과 구분한다.

이 정보의 문서화는 push·배포 또는 중단된 작업의 재개 지시가 아니다. 실행 승인 시 원격 배포를 포함할지 범위를 확정하고, 포함된 경우 아래 배포 조건과 최종 인도 기준을 적용한다. 이전 읽기 연결 성공만으로 실제 배포 완료를 주장하지 않는다.

### 3.5 원격 배포가 실행 범위에 포함될 때

PRD v1.5의 DEPLOY-01을 따른다. 배포 namespace는 `gs-plai-5h`로 확정했다. 배포할 커밋·브랜치와 이미지 레지스트리/이름, Ingress·도메인·TLS, StorageClass/PVC, MQTT 위치·인증을 확정한다. 누락 설정은 기존 자원과 정책을 확인해 결정하되 외부 공개·권한 변경 등 별도 승인 대상은 임의 실행하지 않는다.

네임스페이스 범위의 원격 명령에는 `--context=charles-k3s --namespace=gs-plai-5h`를 명시하고 해당 리소스 매니페스트의 `metadata.namespace`도 일치시킨다. 기본 context를 바꾸지 않는다. 배포 전에 필요한 권한과 노드 아키텍처를 확인한다. 현재 SQLite 단일 writer 구조에 맞춰 앱 1개 인스턴스 및 안전한 교체 전략, 영속 볼륨·백업·복원 경로를 설계한다. 민감정보는 저장소·이미지에 넣지 않고 배포 환경의 Secret 등으로 전달한다.

원격 배포의 인수 기준은 readiness·UI 접근·실제 MQTT 데이터/제어 왕복·재시작 후 영속 복구·이전 정상 버전 복구다. 배포 매니페스트, 이미지 식별자, 소스 커밋과 시험 근거를 연결한다. 로컬 성공과 원격 성공을 각각 기록한다. 원격 환경이 준비되지 않아 배포할 수 없으면 사유와 필요한 입력을 남기고 로컬 완료를 원격 완료로 바꾸어 보고하지 않는다.

배포 구현·검증도 같은 14시간 운영 한도와 종료 30분 전 동결 정책 안에서 수행한다. 마지막 30분에 새로운 배포 구조를 도입하지 않으며, 원격 버전이 미완성이면 원격의 마지막 검증 릴리스를 우선 복원하고 로컬·원격의 최종 버전 차이를 명시한다.

## 4. 필수 제품 범위

세부 의미·범위·기본값·오류 처리는 기준 PRD를 따른다. 다음 기능을 빠뜨리지 않는다.

1. 풍력·태양광·복합 단지와 RTU 등록, 위경도 미입력 시 국내 후보 지역 주변 가상 좌표, CSV/TSV 업로드.
2. 10분 발전 데이터 정규화와 1초 생성, 시점/구간 평균/kWh 의미 구분, KST/UTC 처리, 전압·원본 전류·추정 전류 구분.
3. CSV 재생 및 기상 기반 발전 모델, 정격·램프·기동 지연, 출력 제한·목표 kW·기동·정지.
4. 기상청 현재 관측과 수동 기상 조정, 일사 CSV, 관측 실패/결측/오래된 값 처리. 누적 일사를 순간 일사로 임의 변환하지 않음.
5. 통합 발전 대시보드, 단지 선택 3D, 기상·제어와 출력 변화, 발전기별 상태.
6. 대시보드와 별개인 RTU 디바이스 메트릭, 연결·수집·PUBACK·전송 실패·버퍼·명령 이력.
7. RTU별 독립 MQTT 연결과 전체 SCADA 배치, 기본 60초 전송 및 메시지 크기 제한.
8. VPP 목표값의 검증·중복 방지·유효기간·우선순위·SCADA 전달·목표 도달/실패/시간 초과 구분.
9. SQLite 영속화, outbox, 재시작 복구, 같은 messageId 재전송 및 VPP 중복 제거 예제.
10. RTU별 통신 단절·지연·전송 실패·센서 중단·SCADA 거절·출력 고정 시험.
11. 재생 배속·일시정지·난수 시드, 시나리오 저장·복원·내보내기와 runId 분리.
12. 이벤트 로그, 관리 API, MQTT 연동 가이드 페이지·다운로드 문서·실행 가능한 시험 클라이언트.
13. 기준 PRD에서 채택된 추가 요구의 구현 및 검증. 문서에 제안으로만 남은 항목은 완료 기능과 구분.
14. 자동 시험, 보안·이슈 기록, 버전별 변경 기록, 최종 한국어 소개·시연 영상과 영상 제작 후 작성하는 발표자료 PPT.

예측·입찰 알고리즘 자체, 실제 시장 제출, 제조사 인증 모델, 실물 SCADA 프로토콜, 대규모 운영 인증은 별도 범위다. 실제 VPP/AWS 환경이 공급되지 않았으면 로컬 대체 검증과 실제 환경 미검증을 구분한다. 필요한 외부 입력을 조작하거나 추정해 성공으로 처리하지 않는다.

## 5. 병렬 세션 구성

### 5.1 메인 — 목표·통합·릴리스 책임

작업 분할과 의존성, 우선순위, 충돌 해결, 공통 계약, 아이디어 채택, 버전 승격, 마감·복원, 최종 영상·발표자료 PPT·인도를 책임진다. 목표 완료 여부를 독립적으로 확인하고 담당의 “완료” 보고만으로 최종 완료를 선언하지 않는다.

### 5.2 기능 개발 A — SCADA·발전 모델

CSV·시간·발전기 모델·기상·재생을 담당한다. 계산식과 경계 조건, 모델 단위시험을 함께 제출한다.

### 5.3 기능 개발 B — RTU·MQTT·제어

명령 처리·전체 SCADA·영속화·복구·전송·연동 클라이언트를 담당한다. 실제 브로커 통합시험과 메시지 계약 준수를 증명한다.

### 5.4 기능 개발 C — 대시보드·3D·UX

화면과 조작 흐름, RTU 메트릭, 시험실, 연동 가이드 화면, 3D를 담당한다. 서버 계약을 임의로 변경하지 않고 실제 화면을 검증한다.

### 5.5 PRD·아이디어 담당

PRD의 빈틈, 작업 중 발견한 더 나은 설계와 사용자 가치를 검토한다. 제안 이유·우선순위·예상 영향·수락 조건을 작성하고, 채택 시 PRD와 변경 기록을 갱신한다. 구현자에게 전달하고 결과물 반영 여부를 확인한다. 단순 제안을 구현 완료로 표시하지 않는다.

### 5.6 보안·취약점 담당

신규 OSS·의존성 변경과 관련 소스 변경을 감시하고 취약점 영향·패치 가능성을 조사한다. 격리된 브랜치의 패치 또는 정확한 수정안을 제공한다. 메인이 통합한 뒤 보안 담당이 독립적으로 재검증한다. 적용 불가능한 항목은 취약점 관리 문서에 남긴다.

### 5.7 이슈·해결 기록 담당

문제 발견·재현·분류·담당 배정·진행 추적·해결 근거를 기록한다. 중복 이슈를 연결하고 회귀 여부를 확인한다. 독립 검증 없이 이슈를 닫지 않는다.

동시 실행 슬롯이나 자원 제한으로 모든 역할을 동시에 실행할 수 없으면 메인이 회차를 배정하되 역할과 기록은 유지한다. 별도 세션과 내부 하위 에이전트 중 환경에 맞는 형태를 사용한다. 실제 실행하지 않은 담당을 “상시 감시 중”이라고 표시하지 않는다.

## 6. 병행 작업의 소통·감시 방식

기능 개발은 가능하면 별도 Git worktree/브랜치에서 수행하고 메인이 병합한다. 같은 폴더를 사용하는 모니터는 기본 읽기 전용이며 자기 담당 문서만 수정한다. 파일별 소유자를 정하고 공통 API·스키마·설정·의존성 잠금 파일의 충돌은 메인이 조정한다.

모든 세션에 기준 PRD, 이 목표 문서, 담당 범위, 수정 가능한 파일, 수락 조건, 의존 계약, 현재 버전과 마감을 전달한다. 대화 맥락이나 다른 worktree 변경이 자동으로 동기화된다고 가정하지 않는다.

메인은 작업 단위 완료 시 또는 약 10분마다 담당 상태·문서를 확인하고 다음 검토를 요청한다. 모니터는 일회성 검토로 끝나지 않고 다음 변경 회차에 재호출되어 진행 기간 동안 협업을 이어간다. 감시 대상은 PRD/코드/lockfile 차이, 테스트 실패, 로그, 이슈·취약점 상태 및 채택 아이디어다.

발견한 중요한 오류·취약점·계약 충돌은 정기 회차를 기다리지 않고 메인에 전달한다. 실행 중인 세션에 같은 작업을 반복 발송하지 않는다. 회차마다 검토 범위·기준 커밋·증거·소요 조치·미해결 항목을 남긴다.

서버 포트, DB 파일, MQTT prefix/clientId를 세션별로 분리한다. 운영 중인 데모 데이터를 테스트 fixture로 무단 공유하지 않는다. 안정화·복원·마감 과정에는 모든 세션에 중지 시점을 전달하고 진행 중 변경을 보존한다.

## 7. 아이디어 채택과 목표 재설정

아이디어마다 `IDEA-NNN`을 부여한다. 목적, 해결할 문제, 기존 요구와 관계, 우선순위, 구현 범위, 위험, 의존성, 검증 방법, 예상 작업량, 상태를 기록한다.

상태는 제안 → 검토 → 채택 → 구현 → 검증 → 릴리스이며 보류·거절 시 이유를 남긴다. 채택 시 먼저 PRD 요구와 인수 조건을 갱신하고 담당에게 전달한다. 구현·시험·가이드까지 반영한 뒤 검증 완료로 표시한다.

필수 기능을 조기에 완료했을 때 메인은 PRD 담당 제안을 검토해 남은 시간에 완결 가능한 개선 목표를 선택하고 새 반복의 범위를 기록한다. 데이터·제어의 신뢰성, 연동 편의, 시험 재현성, 보안, 사용성 개선을 우선한다. 목표 갱신은 무제한 범위 확대나 기존 완료 조건의 삭제를 뜻하지 않는다. 동결 전 구현·통합·시험이 끝나기 어려운 아이디어는 다음 버전으로 보류한다.

추가할 가치 있는 변경이 없다면 의미 없는 기능을 만들지 않고 장애·복원 검증, 미해결 이슈 확인, 문서 정합성 및 시연 준비를 진행한다. “14시간을 채우기 위한 변경”은 만들지 않는다.

## 8. 버전·변경 관리

다음 버전을 분리한다.

- 목표 문서 버전: 운영 규칙 변경 시 증가.
- PRD 버전: 아이디어 추가 또는 요구 변경을 정식 반영할 때 증가. 후보만 등록하는 경우도 아이디어 목록 revision과 변경 기록을 남김.
- 제품 버전: 구현·검증 완료 기능의 릴리스. 기능 추가는 minor, 호환 수정은 patch, 호환 파괴는 major를 기준으로 판단.
- MQTT/API/보고서 스키마 버전: 외부 계약 변경 여부에 맞춰 별도로 관리.

아이디어 → PRD 변경 ID → 이슈/보안 항목 → 작업 커밋 → 시험 증거 → 릴리스 버전으로 추적 가능해야 한다. PRD는 완료된 제품 설명과 미래 요구를 구분한다. 정식 채택되지 않은 후보를 현재 필수 기능 목록에 조용히 섞지 않는다.

검증된 제품 커밋에 `stable-vX.Y.Z` 태그를 부여한다. 태그를 새 커밋으로 덮어쓰지 않는다. 작업 중 변경은 commit/branch/archive로 보존하고 검증되지 않은 작업본을 stable로 지정하지 않는다.

## 9. OSS 보안과 취약점 관리

새 패키지 추가·버전 변경·lockfile 변경 시 신규/변경/제거 의존성을 파악하고 개발 의존성까지 검사한다. 패키지명·직접/간접 경로·설치 버전·lock hash·검사 도구와 시각·원본 결과를 기록한다. npm audit만으로 Node 런타임·컨테이너·애플리케이션 전체가 안전하다고 판정하지 않는다.

취약점은 공식 권고와 실제 영향 버전·사용 경로·실행 도달 가능성을 대조한다. 버전 문자열이 비슷하다는 이유만으로 영향 패키지가 없는 취약점을 적용하지 않는다. 조회 실패나 도구 실패를 취약점 0건으로 표시하지 않는다.

적용 가능한 패치는 최소 변경으로 구현하고 관련 회귀시험·전체 통합·빌드를 통과시킨다. 무조건적인 force 업그레이드, 인증/TLS 비활성화, 검증 없는 대규모 의존성 교체는 하지 않는다. 호환 문제로 패치가 어려우면 대체 패키지·기능 격리·설정 완화를 검토한다.

미적용 취약점 문서는 다음을 포함한다.

- `SEC-NNN`, 최초 발견/최근 확인 시각, 관련 제품 버전
- 패키지·설치 버전·의존 경로 또는 소스 위치
- CVE/GHSA·공식 URL, 심각도와 판단 근거
- 실제 영향·공격 전제, 검증한 범위와 미검증 범위
- 패치/안전 버전, 적용 불가능한 이유
- 현재 완화책, 잔여 위험, 재검토 조건, 담당
- 상태와 해결 커밋·검증 증거

패치 미제공·환경 자격증명 부재·호환성·잔여 시간 부족을 각각 구분한다. 해결할 수 없으면 숨기지 않고 최종 인도에 포함한다. 기존 취약점 기록을 삭제하여 목록을 비우지 않는다.

## 10. 이슈와 해결 과정 관리

`ISSUE-NNN`별로 발견 버전·심각도·증상·재현 절차/fixture·기대/실제·영향·근거·담당·상태를 기록한다. 원인 가설과 확인된 원인을 구분하고, 수정 접근·변경 커밋·회귀시험·검증자·잔여 사항을 시간순으로 보존한다.

상태는 OPEN → TRIAGED → IN_PROGRESS → FIXED → VERIFIED → CLOSED를 기본으로 한다. 근거 부족 또는 재현 실패는 명시하고, 수정 후 재현과 회귀검증 없이 CLOSED로 표시하지 않는다. 재발 시 기존 항목을 연결해 REOPEN한다.

제품·보안·사용성 이슈가 겹치면 기록을 연결하고 서로 다른 상태로 방치하지 않는다. 단위시험 성공만으로 실제 MQTT·브라우저·복구 범위까지 성공했다고 확대 해석하지 않는다.

## 11. 자율 결정 범위와 외부 의존성

AI는 기존 목적과 계약 안에서 구현 방법, 모듈 분리, 시험 구성, 작은 UX 개선, 패치 순서, 추가 아이디어 채택을 자율 결정한다. 일상적인 선택마다 사용자 응답을 기다리지 않는다.

하지만 Goal은 접근 권한이나 결제·외부 전송·운영 배포 권한을 확대하지 않는다. 유료 서비스 구매, 공개 배포, 실제 운영 발전기 제어, 외부 계정 권한 변경 등 별도 승인 대상은 자동 승인으로 간주하지 않는다. 키·인증서·외부 시스템 계약이 없으면 해당 의존성을 기록하고 로컬 대체 시험 등 독립 가능한 작업을 계속한다.

불확실한 값은 PRD 기본값 또는 명시한 가정을 사용한다. 사실 확인이 필요한 보안 권고·외부 프로토콜은 공식 자료로 검증한다. 실제 실행하지 않은 시험이나 미연결 시스템을 완료로 보고하지 않는다.

## 12. 14시간 운영 정책

실행 시작 시 확정한 T0를 기준으로:

- **T0:** 현재 상태 보존, 기준선·역할·수락 조건 확정과 작업 시작.
- **T0~T0+13시간30분:** 필수 구현·시험과 채택된 개선 반복. 안정 버전을 수시로 확보.
- **T0+13시간30분:** 새 기능·의존성 추가 동결, 정상 버전 확정 또는 복원.
- **마지막 30분:** 확정 결과물의 시연 영상 제작 → 발표자료 PPT 작성 → 두 산출물 검증·문서·인도.
- **T0+14시간:** 개발 종료, 담당 작업과 이번 실행의 예약 정리, 실제 산출물 인도.

시작·마감은 UTC와 KST를 함께 기록한다. 시작 시각은 문서 작성 시각이나 과거 취소된 일정에서 계산하지 않는다. 사용자 일시중지·재개 시 마감 연장 여부를 임의 결정하지 않고 사용자의 지시를 확인한다.

매 작업 단위 시작/종료 및 재개 시 실제 시각을 확인한다. 동결에 가까워지면 장기 작업을 새로 시작하지 않는다. 정확한 마감보다 개발 완료가 늦을 것으로 보이면 기능 범위를 조용히 삭제하지 않고 미완성 버전을 보존한 채 검증 버전 인도를 준비한다.

Goal 자체는 정밀 타이머가 아니며 앱·네트워크·컴퓨터 중단에 따른 지연 가능성이 있다. 가능한 예약·재개 수단과 시간 점검을 조합하되 보장되지 않는 정시 실행을 약속하지 않는다. 마감 이후 늦게 재개되면 새 개발을 시작하지 않고 지연·최종 상태·미완료 산출물을 보고한다. 시간을 임의 연장하거나 이전 14시간 일정을 반복 실행하지 않는다.

## 13. 안정 버전과 비파괴 복원

기준선과 각 stable 승격 시 커밋·PRD 버전·lockfile·환경 예시·검증 로그·DB 스키마 및 일관성 있는 DB 백업을 보관한다. SQLite는 backup API 또는 정상 종료 후 안전한 백업을 사용하고 WAL 사용 중 본 DB 파일만 복사해 완전한 백업으로 간주하지 않는다.

원격 배포를 수행한 경우 체크포인트에 이미지 digest/태그, 매니페스트, context/namespace와 PVC·DB 백업도 포함한다. Git 소스만 되돌리는 것으로 클러스터와 데이터까지 복원되었다고 판단하지 않는다.

최종 동결 점검에서:

1. 담당 세션의 새 변경을 멈추고 작업본·로그·DB를 보존한다.
2. 현재 버전이 해당 범위의 필수 시험과 실행 확인을 통과했는지 판정한다.
3. 통과하면 최종 버전으로 확정한다.
4. 미완성이거나 검증이 부족하면 마지막 검증 stable을 별도 작업폴더 또는 릴리스 경로로 복원한다.
5. DB 호환성을 확인하고 필요하면 해당 버전의 백업 DB를 분리 복원한다.
6. 실제 실행·핵심 MQTT 경로·주요 화면을 확인하고 영상 대상 버전을 고정한다.

사용자 변경을 `reset --hard`, `clean` 등으로 폐기하지 않는다. 실패 버전도 별도 브랜치/아카이브에 보존한다. 전체 목표를 만족하는 stable이 끝내 없으면 동작 가능한 범위와 미완료를 보고하고 완성이라고 표시하지 않는다.

## 14. 시연 영상 요구사항

최종 30분에 확정한 정상 버전을 기반으로 새로운 시연 영상을 제작한다. 캡처 도구·레이아웃·나레이션 초안·렌더링 도구는 미리 준비할 수 있지만 과거 영상만 복사해 최종 버전 시연으로 제출하지 않는다.

### 내용

- 에뮬레이터가 해결하는 문제와 외부 예측/입찰·제어 시스템과의 경계.
- 10분 CSV 입력 → 1초 데이터 → RTU 전체 SCADA 전송.
- 풍력·태양광·복합 단지, 3D·기상 조작과 발전량 변화.
- 통합 대시보드와 RTU 디바이스 지표의 차이.
- 실제 MQTT 목표값 전송 → 접수 → SCADA 전달 → 출력 도달/실패 결과.
- 장애 주입·재전송·복구와 시나리오 재현.
- 실제 VPP 연결을 위한 가이드와 미검증 운영 범위.
- 최종 버전에 반영한 핵심 개선과 버전 정보.

### UI/UX 표현

실제 UI 조작을 사용하고 마우스 포인터 이동과 클릭 위치를 시청자가 따라갈 수 있게 표시한다. 중요한 버튼·입력·결과는 확대하고 전체 맥락으로 돌아올 때 축소한다. 포인터·확대는 실제 조작 대상과 맞아야 하며 화면 결과를 가리거나 작동하지 않은 기능을 동작한 것처럼 연출하지 않는다. 정지 캡처만의 나열로 전체 조작 시연을 대체하지 않는다.

한국어 내레이션과 자막, 읽을 수 있는 글자 크기와 속도, 1080p MP4(H.264/AAC)를 기본으로 한다. 분량은 핵심 흐름을 설명할 수 있도록 구성하며 기존 약4분 결과물을 참고할 수 있다. SRT·원고·장면 구성·제작 소스·대표 프레임을 함께 보관한다. 키·계정·개인정보는 촬영하지 않는다.

디코딩·해상도·길이·음성 트랙을 확인하고 시작/중간/끝 및 실제 클릭·확대 장면을 직접 검토한다. 내레이션과 화면·검증 결과가 일치해야 한다. 시연 후 장애·제어 설정을 의도한 인도 상태로 복원한다.

### 시연 영상 다음 단계: 발표자료 PPT

시연 영상 제작이 완료되면 같은 최종 정상 버전과 영상의 실제 결과를 근거로 한국어 발표자료를 작성한다. PRD 22장의 PPT-01~03과 AT-PPT-01~03을 따른다. 기본 산출물은 편집 가능한 16:9 `.pptx`이며 12~15장 내외, 약 10~15분 발표를 기준으로 구성한다. 장수보다 필수 내용과 가독성을 우선한다.

발표자료에는 배경·요구사항·목표, 외부 VPP와의 시스템 경계, 양방향 MQTT 아키텍처, CSV→1초 SCADA→RTU 전송, 목표값 제어 및 결과 피드백, 주요 UI·3D·RTU 메트릭, 장애·복구, 연동·배포 방법, 검증 결과, 보안·이슈·제약, 버전별 개선 및 다음 과제를 포함한다. 실제 최종 UI 캡처와 구조도를 사용하고 발표자 노트에 설명과 시연 영상의 파일명·관련 타임코드를 기록한다. 로컬 검증과 실제 VPP/AWS/k3s 검증 상태를 구분한다.

슬라이드 개요·템플릿·생성 도구는 동결 전에 준비할 수 있다. 최종 내용 확정과 PPT 제작은 영상 다음에 진행하며, 영상·PPT·검증 모두 기존 마지막 30분과 총 14시간 한도 안에 포함한다. 시간이 부족하면 미완료 상태를 보고하며 임의로 마감을 연장하거나 산출물을 생략하고 완료로 표시하지 않는다.

최종 PPT를 열고 모든 슬라이드를 렌더링하여 잘림·겹침·폰트·캡처 해상도·가독성을 확인한다. 수치·버전·검증 주장을 최종 실행 근거 및 영상과 대조하고 수정 후 다시 확인한다. PPT, 발표자 노트, 재생성에 필요한 소스·사용 자산과 검수 기록을 인도한다. 영상은 함께 제공하며 영상 연결 시 다른 컴퓨터에서도 찾을 수 있는 상대 경로와 파일명 안내를 사용한다.

## 15. 검증과 완료 판정

PRD의 필수 요구와 인수 조건을 요구 ID별로 구현 위치·시험·실행 로그·화면 증거에 연결한다. 기준 명령은 npm test, npm run test:integration, npm run test:advanced, npm run build이며 추가 기능 시험도 수행한다. 실행 방법이 변경되면 문서와 스크립트를 함께 갱신한다.

자동 시험만으로 UI 완료를 선언하지 않고 실제 브라우저에서 주요 흐름을 확인한다. 실제 MQTT와 임시 DB로 단절·중복·실패·복원을 확인한다. 보안 담당의 검토 결과와 미해결 목록을 확인하고 새로운 의존성 변경이 검사에서 빠지지 않았는지 대조한다.

목표 완료는 파일 존재만으로 판정하지 않는다. 기능 동작, 결과의 정확성, 문서 정합성, 복원 가능성, 영상·발표자료 내용과 실행 증거를 확인한다. 시간이 끝났다는 사실은 작업 종료 조건이며 모든 기능의 성공을 뜻하지 않는다. 미완료가 남으면 “시간 종료·부분 완료”로 보고한다.

## 18. 현재 상태와 실행 금지 확인

이 문서의 작성 요청은 작업 진행 요청이 아니다. 시작 시각 T0는 **미정**, 목표 활성화는 **미승인**, 세션/예약 재개는 **미승인**이다. 실행 관련 기존 기록은 보존하되 새로운 출발 시각과 기준선이 명시되기 전에는 사용하지 않는다. 이 문서 작성 후에는 문서 링크와 포함 범위만 전달한다.
