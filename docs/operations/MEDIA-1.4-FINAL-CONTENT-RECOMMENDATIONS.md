# 안정1.4 최종 미디어 문구 준비 권고

준비 검토만 수행했다. 현재 기준은 [1.4 체크포인트](../../artifacts/releases/checkpoint-1.4.0.json)의 제품1.4.0 / PRD1.11, 앱 runtime `fdd0491a5c08901962f46ac845f8582921150d45`, 이미지 `sha256:c19d550f0cfabbeb1e5f637f3c38a1daee1c2c44222b68dd088ae1875cd4b4f4`다. 최종 내용은 동결 시 실제 선택 매니페스트를 다시 기준으로 삼는다. 운영/미디어 소스를 포함한 release.source.commit과 앱 runtime commit을 같은 값이라고 표현하지 않는다. 이 문서는 스크립트·기존 템플릿·원본 일정·앱을 변경하거나 최종 영상/PPT를 생성하지 않는다.

## 기존8장면에서 실제로 보여주는 범위

현재 흐름은 CSV 해석 미리보기/신규 RTU 등록, 풍력·태양광·복합 선택과3D 시점, 상한·기동·정지, RTU 메트릭, 별도 MQTT125kW 및 최근 명령 상태 다운로드, 통신·센서 장애, 시나리오 저장/복원, 가이드다. 명령 결과 탭에 새 일반 REST 목표 폼이 보일 수 있지만 해당 폼의 값을 제출하거나 오류를 재현하지 않는다. 따라서1.4의 입력 범위·날짜 오류 안내는 **별도 시험으로 검증한 개선**으로 소개하며 이 영상에서 시연했다고 말하지 않는다. 실제 폼 동작 소개를 추가하려면 별도 장면 조작과 검증이 필요하며 현재 일정에 자동 추가하지 않는다.

## 최종 내레이션에 필요한 조정

장면1의 최종 문구는 다음처럼 구체화할 수 있다. “GRID 제품 일 점 사는 가상 발전 현장에서 외부 VPP 연동을 시험하는 에뮬레이터입니다. 지금은 동결한 케이쓰리에스 배포 화면입니다. 실물 설비를 조작하거나 시장에 입찰하지 않습니다.” 동결 버전이 바뀌면 버전 부분도 바꾼다.

장면2의 CSV 미리보기와 장면5의 별도 MQTT/최대20개 저장 상태 설명은 현재 문구를 유지한다. REST 입력 범위 검증과 MQTT125kW 결과를 같은 시험으로 묶지 않는다. 실제 completed125/error0과 commandId는 최종 보고서에서 확인한다.

장면6의 현 템플릿은 ‘손실 주입’과 ‘재시작 뒤 재전송’을 설명하지만 실제8장면은 dropPct를 변경하거나 서버를 재시작하지 않는다. 최종 문구 권고: “통신 단절과 지연, 센서 중지를 구분해 시험합니다. 센서가 멈춘 구간은 결측으로 남습니다. 미확인 배치의 재시작 복구는 함께 제공하는 별도 실행 근거에서 확인할 수 있습니다.” 이전 시험 결과를 소개할 때는 선택 매니페스트의 정확한 outbox/복구 근거를 연결한다. 이 영상 자체에서 재시작 복구를 재현했다고 말하지 않는다.

장면7 권고: “배속과 일시정지, 난수 시드로 시험 조건을 조절합니다. 선택한 RTU의 시나리오를 복원하면 새 실행 식별자가 생깁니다. 이전 실행은 runId로 구분하며 기존 outbox를 삭제하지 않습니다. 가이드에서 이 RTU의 토픽과 규격을 확인합니다.” ‘이전 샘플을 섞지 않는다’보다 실제 식별·보존 의미를 정확히 설명한다.

장면8은 기존 미검증 범위를 유지한다.1.4 개선을 영상에서 반드시 언급하려면 짧게 “일반 목표 입력의 범위와 날짜 오류 안내는 별도 시험으로 확인했습니다. 이 영상의 출력 제어는 별도 MQTT 클라이언트 결과입니다.”라고 덧붙일 수 있다. 해당 인수 근거를 확정하지 못하면 앞 문장을 넣지 않는다. KMA 요청 완료는 새 실관측 적용 증거가 아니며 외부 KMA/AWS/운영 VPP 미검증을 유지한다.

## 최종 facts와14장 발표자료의 조정

검토 시작 시 facts.template.json의 productVersion은1.3.0이고 reviewed:false/preparationTemplate:true였다. 최종1.4 선택 시 복사한 facts에서 productVersion=1.4.0, prdVersion=1.11로 바꾸고 실제 영상/장면/명령 보고서/캡처 해시와 선택 RTU·demo-recovery 전환을 채운다. 검수 후에만 reviewed=true로 바꾼다. 기존 리허설 캡처나 prepared facts 해시를 최종값으로 쓰지 않는다.

- 1장 표지: 제품1.4.0 / PRD1.11과 동결 릴리스. runtime과 운영 소스 커밋은 구분한다. 영상/이미지 해시를 바인더가 연결한다.
- 5장 CSV: 실제 최종 csv-preview 캡처와 등록 장면 시각. 원본 시간·단위·전류 출처 구분을 유지한다.
- 6장 목표 제어: 실제 MQTT125kW 상태 전이와 다운로드 근거. 노트에 “일반 REST 폼의 입력 오류 시험은 별도 인수 근거이며 이 장면에서 수행하지 않았습니다.”를 넣는다. 현재 command-export 캡처가 새 폼을 함께 보여도 오류 재현 증거로 쓰지 않는다.
- 7장 대시보드:3D·발전 유형·제어 실제 화면. 기상 패널이 보인다는 이유로 KMA 성공을 주장하지 않는다.
- 8장 RTU: 발행 시도/PUBACK/대기 수를 구분하며 PUBACK를 운영 VPP 업무 수신 완료라고 표현하지 않는다.
- 9장 장애: 실제 통신/센서 조작과 별도 outbox·백업 시험을 구분한다. 시연 종료 상태 복원은 source/demo-recovery.json의 PASS 및 기존 RTU 불변을 근거로 한다. 무작위 궤적의 완전한 원상 재현을 주장하지 않는다.
- 10장 시나리오: 선택 RTU 필터와 실제 observed before/after runId. 일반 설명 대신 최종 기록을 사용한다.
- 11장 배포: 최종 선택 매니페스트의 runtime fdd 계열·이미지 c19 계열 여부를 재확인하고 정확한 전체 값/접속 절차/검증된 백업 근거를 노트에 연결한다. 후보/과거1.3 접속·복구 기록과 혼동하지 않는다.
- 12장 검증: 최종 영상의 실제 관측과 선택 manifest에 있는 별도 시험을 구분한다. 수동 작성한 시험 개수는 최종 인수 근거가 없으면 생략한다.
- 13장 보안/이슈: 최종 선택 버전의 관리 문서와 잔여 이슈. 현재 기능 인수 성공을 최종 미디어·전체 시간 목표 완료로 확대하지 않는다.
- 14장 개선 본문 권고: “CSV 미리보기 · 최근 명령 상태 내보내기 · 선택 RTU 시나리오 · 일반 목표 입력 안내”. 노트: “1.4는 기존 서버 범위와 날짜 오류를 입력 단계에서 안내합니다. 소수와0초 의미를 유지하며 조용히 값을 보정하지 않습니다. 새 폼의 오류/수정/키보드 경로는 별도 실제 브라우저 인수 근거로 확인했고, 본 영상에서는 제출하지 않았습니다.” 정확한1.4 인수 기록이 선택 manifest에 포함되는지 확인한다.

2~4장의 목적·경계·편집 가능한 아키텍처 설명은 유지한다. 모든 장의 시간표시는 최종 scenes.json에서 계산한다. 영상에 직접 없는 배포/보안/과거 시험 슬라이드의 타임코드는 관련 개요 장면으로 안내하고, 그 시각에 해당 시험을 재현했다고 설명하지 않는다.

## 남은 실행 연결

문구 수정은 동결 전 준비 파일로 할 수 있으나 실제 최종 facts와 캡처 연결은 새 영상 검수 다음에 수행한다. 원래 마지막30분 안에서 영상 → 복구 확인 → 최종 facts 바인딩 → PPT 제작 →14장 검수 순서를 유지한다. 준비용 문구 변경만으로 reviewed/pass를 기록하지 않는다. 이번 검토에서는 소스가 변경되지 않아36개 시험이나 렌더를 반복하지 않았다.

## 준비 문구 반영 완료

scenes-template.json의6/7장면을 위 범위 구분 문구로 수정했다. facts.template.json은1.4.0/PRD1.11 준비 기준으로 바꾸고6장·9장·11장·14장의 노트와 정확한 fdd0491 outbox/안정 백업/독립 복구/복구본 명령 폼 근거 후보를 연결했다. 선택1.4 체크포인트의 각 evidence SHA와 파일이 일치함을 확인했다. reviewed:false/preparationTemplate:true 및 실제 영상·장면·보고서·캡처·RTU·runId 자리표시자는 유지했다. 실제 최종 facts는 동결 후 새 영상과 복구 기록을 검수해 완성한다.

scenes-template.json의 artifacts/releases/current.json 기본값은 이번에 바꾸지 않았다. 로컬 prepare-rehearsal.cjs가 이 값을 상속하고 별도 대체하지 않으므로 임의 placeholder로 바꾸면 기존 준비 흐름이 깨진다. 최종 prepare-final-scenes.cjs는 입력받은 선택 매니페스트로 이 필드를 명시적으로 덮어쓰고 릴리스 바인딩을 검사한다. 따라서 최종 실행은 메인이 확정한 입력 매니페스트를 사용해야 하며 오래된 current.json을 그대로 승인하지 않는다. final-input-template.json과 바인더 코드는 이번 소유 범위에서 수정하지 않았다.
