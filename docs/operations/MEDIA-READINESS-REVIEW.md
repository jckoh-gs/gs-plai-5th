# 최종 미디어 준비 검토

범위: 제품1.3 정상 버전을 대상으로 기존 제작 흐름과 GOAL §16, PRD22/FR-FAULT-02를 읽기 전용 검토했다. 최종 동결21:37:33Z·마감22:07:33Z는 유지한다. 이 검토는 도구 수정·녹화·PPT 렌더·배포를 수행하지 않았으며 최종 성공 판정이 아니다.

## 실제 시연 순서

현재 `prepare-final-scenes.cjs`는 확정 매니페스트·API 버전을 확인하고 기존 풍력/태양광 이름과 고유한 새 복합 단지/시나리오 이름을 만든다. 실제8장면은 기존 풍력 선택 → CSV 미리보기와 새 복합 RTU 등록 → 3D/풍력/태양광 선택 및 새 복합의80%/정지/기동/100% 제어 → 새 복합 RTU 메트릭 → 지연1500ms와 별도 MQTT125kW/명령 JSON 내보내기 → 통신/센서 장애 주입·해제 → 배속2→1, seed777, 일시정지/재생, 저장·복원 및 가이드 → 최종 대시보드다. 기존 풍력/태양광은 선택만 하며 의도적으로 설정을 바꾸지 않는다.

## 확인한 공백과 최소 준비

1. **시연 전 기준 상태와 정확한 소유 RTU 기록이 없다.** 바인더가 읽은 `/api/state`를 보존하지 않고 새 RTU의 이름만 만든다. 녹화기 dispatch/download는 현재 UI 선택 ID를 읽지만 시연 전체의 허용 대상 ID 목록을 유지하지 않는다. 최소 준비는 녹화 전 기존 RTU별 모델·제어·재생·장애 설정의 비밀 없는 기준 JSON과 해시, 기존 ID 집합을 저장하고 UI 등록 응답에서 얻은 새 ID를 전용 journal에 즉시 기록하는 것이다. 이름만으로 정리 대상을 찾지 않는다. baseline은 매초 바뀌는 출력/시계/샘플 카운터를 제외한 복원 가능한 설정에 집중한다.

2. **정상 종료도 원래 제어 상태 복원이 아니다.** 장애 해제는 있으나 MQTT125kW 제한이 남는다. seed777과 scenario restore가 만든 freezeLiveWeather=true도 남으며, 저장한 시나리오는 원래 등록 직후 상태가 아니라 시연 중 상태다. 마지막100% 상한 적용만으로 targetLimitKw가 없어졌다는 보장이 없다. 최소 준비는 새 RTU 등록 직후의 설정을 기준으로 저장하고, 성공/실패 후 그 설정을 정확히 복원하는 명시적인 정리 절차다. 기존 RTU는 변경 없음 비교로 검증한다. 복구 명령의 수락만으로 끝내지 말고 실제 최종 저장 상태와 장애 필드·제어 목표·재생 조건을 대조한다. 샘플/명령 이력/outbox는 증거이므로 일괄 삭제하지 않는다.

3. **중단·마감 강제 종료 후 서버 상태 정리가 없다.** 녹화 catch는 브라우저만 닫는다. 동기 도구 또는 watchdog의 강제 종료는 finally조차 보장하지 못하므로 recorder 안의 finally만으로 해결되지 않는다. 최소 준비는 소유 ID·등록 직후 baseline·수행 단계가 담긴 디스크 journal과 별도 bounded cleanup 명령이다. 메인이 recorder 성공/실패와 관계없이 journal을 확인해 마감 전 정리를 실행하고 검증 기록을 남겨야 한다. 정리 시간을 미리 예약하고 녹화를 마지막 순간에 시작하지 않는다. 종료 시각 이후 자동 연장하지 않으며 실패하면 FR-FAULT-02 미완료로 보고한다.

4. **'모든 시험 단지 장애 해제'의 대상 정책이 명시되지 않았다.** 과거 시험 RTU나 기존 사용자 RTU를 무차별 초기화하면 기준 상태를 훼손한다. 최소 준비는 메인이 최종 시험 RTU ID 목록을 확정하고, 이 목록에는 장애 해제/기준 설정 복원을 적용한다. 나머지는 기준 설정과 불변 비교만 한다. 시연 시작 전 기존 이상 상태는 별도로 기록하고, 시연이 만든 문제인 것처럼 복원하지 않는다. 새 전용 RTU를 남길지 지울지는 명시해야 하며 현재 도구는 삭제를 수행하지 않는다. 최소 보존 방안은 명확히 시연 전용으로 남기고 등록 직후 설정으로 복원하는 것이다.

5. **최종 PPT 설정 완성은 여전히 수작업이다.**14장 템플릿은 필수 구성과 노트를 갖췄지만 본문/실제 타임코드/이미지/실행 근거 자리표시자가 남는다. 최종 내용이 동결 전 확정되지 않은 것은 올바르다. 최소 준비는 각 슬라이드에 사용할 최종 영상 source/scene-N.png 또는 세부 캡처, 실제 scenes.json의 lead+start/end, 최종 릴리스/수락/배포/보안/이슈 근거의 대응 목록을 미리 결정하는 것이다. 최종 생성은 영상 검수 뒤에만 한다. 복원 슬라이드는 기존 배포 복구 시험과 시연 후 상태 정리를 구분하고, 기존 리허설 캡처를 최종 이미지로 재사용하지 않는다.14장 기준 모든 슬라이드 개별 육안 검수와 타임코드 재생 확인 시간이 필요하다.

6. **최종 증거 묶음에 정리 결과 연결이 빠져 있다.** 현재 원본 영상/음성/캡처, 입력 설정/소스/CSV, 영상/PPT 해시와 검수 기록 보존은 준비됐다. 여기에 baseline·소유 ID journal·정리 전후 비교/완료시각을 최종 인벤토리와 FR-FAULT-02 근거로 연결해야 한다. `DELIVERY-PLAN.md`의 백업 복구 링크만으로 시연 종료 상태 복원을 대신할 수 없다.

## 소유권 협의 후 필요한 최소 작업

메인이 baseline/시험 ID 범위와 새 RTU 잔존 정책을 결정한다. 그 뒤 별도 운영 helper가 기준 캡처·journal·bounded 정리·검증을 담당하고 recorder는 등록 ID/진행 상태만 기록하도록 작은 연결을 추가하는 안이 적절하다. 실제 제어 상태 복원에 사용할 기존 API 계약과 targetLimitKw 초기화 의미를 먼저 확인해야 한다. API가 원상 복원을 지원하지 않으면 검증된 시나리오 복원 후 freezeLiveWeather 등 강제 변경 필드를 별도로 되돌리는 방식이 필요한지 시험해야 하며, 임의 DB 수정이나 전체 백업 되감기를 기본값으로 삼지 않는다.

현재 미디어 장면 선택자/1.3 버전 분기는 이전 검토와 일치한다. 새 전체 리허설이나 PPT 렌더는 이 검토에 필요하지 않았다. 위 공백이 닫히기 전 FR-FAULT-02를 최종 통과로 표시하지 않는다.


## 준비 보완 검증 결과

상기 공백은 신규 lifecycle journal/helper·독립복구 CLI·recorder 실제201/200 응답 연결·90초 정리 예약·같은 영상 facts 바인더·납품 검사로 보완했다. 종합 근거는 artifacts/checkpoints/final-media-lifecycle/summary.json이다. 관련65개와 보존/릴리스 연결11개 시험이 통과했다. 로컬 실제 UI 첫 시연 실패 후 소유RTU만 복구했고, 위치가 바뀐 버튼 클릭 처리를 고친 재시험은30.17초 영상 전체디코딩/시나리오 새run/설정복구/기존19RTU불변을 확인했다. 해당 실행 뒤 clock-skew와 실제POST본문 보호를 추가해 별도 fixture로 검증했으며 실제영상 실행소스를 그 이후 소스로 소급하지 않는다.

PPT의 facts·바인더 소스 보존은 실제14장 생성 및 인도 폴더 기준 재생성으로 시험했다. 두 패키지의 보존20파일 해시/원본facts바이트/전체렌더 검사를 통과했고14장 렌더이미지가 같았다. 보안 검토의 초기 실패 입력과 개선 후 결과를 모두 남겼다. 이 결과는 제작 준비 검증이다. 동결 후 실제 배포 영상/설정 복구/전체 미디어 검수 전 FR-FAULT-02 또는 최종 인도를 통과로 바꾸지 않는다.
