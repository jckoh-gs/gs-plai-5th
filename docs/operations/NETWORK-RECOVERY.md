# Network interruption and reconnection

`node scripts/connection-supervisor.mjs` supervises local access to the existing k3s runtime. It does not create, restart, scale, apply, or delete Kubernetes workloads, replay commands, import data, or restore a database. A client network interruption does not itself stop the remote emulator or its persistent MQTT outbox.

The authoritative expectations are reread from `docs/operations/run.json`: context `charles-k3s`, namespace `gs-plai-5h`, deployment `grid`, immutable app image, product version, freeze and deadline. The API credential is read from the ignored `artifacts/private/deploy/api-token`; it is never placed in a command line, status file, or event record.

On each verification, the supervisor checks the Deployment image and the single Ready application's actual kubelet image ID. It then checks API health/configuration, authenticated read-only `/api/state`, expected version, connected MQTT gateway and the local MQTT TCP port. A successful TCP connection alone is not reported as recovery. Each outage-to-ready transition requires the complete checks again. Image mismatch or missing readiness blocks resumption and does not trigger an automatic rollback or deployment change.

An existing healthy localhost `3104`/`18884` forward is adopted for observation without changing its process. If access fails, the supervisor starts its own `kubectl port-forward` only when both ports are free. It only terminates children it created. Occupied, unverified ports are reported as `ports_occupied_unverified`; unrelated processes and borrowed forwards are never killed. A borrowed broken forward that retains its listeners requires the owning main session to resolve it. For fully managed reconnection, the main session may deliberately hand off its own forward after validating the supervisor; this is not done automatically.

Retries use exponential backoff from 1 second to a maximum of 30 seconds. An owned forward receives a 15-second startup grace period. Healthy verification repeats every 10 seconds. Read-only kubectl requests and HTTP requests have time limits. Failed operations are not assumed to have succeeded. Retry does not reset the overall run deadline.

At freeze, `commandsAllowed` becomes false while connection verification may continue until the deadline. This field is informational and is not authorization: the main resume policy must independently compare current time with `freezeAt` and `deadlineAt` before doing any work. The supervisor itself never performs mutating work, even before freeze. At the deadline it stops only its own forward and exits; existing borrowed forwards and the remote workload are retained. An unreadable initial run file fails closed. A later unreadable file stops owned forwarding and retains the last known deadline while awaiting a corrected file.

The ignored `artifacts/operations/` directory contains mode-0600 atomic `status.json`, transition-only `events.jsonl`, and a singleton lock. Status includes PID and process start identity, outage/reconnect timestamps, expected image/version and next retry delay. A PID is not treated as proof of identity by itself. Live matching locks prevent duplicate supervisors; a confirmed dead or reused PID lock is reclaimed under a separate reclamation mutex. Incomplete/corrupt locks and an interrupted reclamation mutex fail closed for inspection. No raw API body, kubectl stderr, token, or connection credential is logged. Copy selected status/log evidence into a versioned checkpoint when needed; do not erase historical outage counters in the separate soak observer.

The supervisor restores transport and verifies state. It cannot revive a terminated Codex session or choose which unfinished work to replay. The main session's persisted resume ledger and native heartbeat own that decision; they must recheck current deployment, stable checkpoint, deadline and work state, and never duplicate an uncertain write merely because a response was lost.

Validation uses `node --test tests/supervisor.test.js` with an isolated fake kubectl executable, fake Kubernetes responses and loopback API/MQTT fixtures. Tests simulate outage/recovery without turning off the user's network, verify bounded backoff and image mismatches, preserve unrelated/adopted listeners, enforce singleton process identities, and check freeze/deadline shutdown behavior. No real deployment is changed by these tests.

## Interrupted backups

`scripts/remote-backup.mjs` bounds each kubectl child and shares a three-minute network/transfer budget capped by the original `run.deadlineAt`. Discovery and identity requests allow at most20seconds, snapshot/compression requests90seconds, and each1MiB compressed chunk15seconds, always shortened by the remaining total budget. A chunk is attempted at most three times. Length, chunk SHA256, compressed-file SHA256, decompressed SQLite SHA256/integrity and the same Ready pod identity must still pass.

Before remote work, the tool writes a mode0600 operation journal under ignored `artifacts/operations/backups/`. On a lost response, inspect that journal's exact remote path and stage before resuming. A new remote snapshot is created privately as `.snapshot.part`. The source must be WAL; a read-only `BEGIN` plus schema read fixes a consistent read snapshot while concurrent commits can continue. Progress callbacks check both absolute and monotonic deadlines. An independent remote parent supervises its own worker for at most80seconds, capped by the original remaining budget, inside the90second host exec allowance. It requests TERM/KILL only on that tracked live child; confirmed exit0, verified integrity IPC and deadline checks are all required before the parent publishes the final `.sqlite` through a non-overwriting hard link. A partial file is never a resumable snapshot. A completed final snapshot can be inspected and retransferred with `REMOTE_BACKUP_PATH` and a new `BACKUP_METADATA_PATH`; this does not recreate the database snapshot. Each transfer uses a separate compression path. Existing metadata is never overwritten and an existing local copy is preserved under a previous-transfer name before replacement.

Local kubectl termination does not prove that its remote process stopped. Snapshot worker progress can cooperatively abort, and the separate parent can terminate a worker blocked in synchronous copying or integrity verification. The parent emits INCOMPLETE and exits at its remaining allowance if worker exit cannot be confirmed; this does not claim the worker has stopped in uninterruptible kernel I/O. External SIGKILL, host shutdown or a blocked/unscheduled parent remain outside this guarantee. The parent checks the deadline immediately before snapshot promotion, and the local process checks it before publishing PASS; the check and hard link are separate operations. The subsequent metadata integrity/compression phase still has host timeouts without this independent worker supervisor. Thus observed deadlines and network waits are bounded, but no absolute cancellation or180second process-exit guarantee is claimed. Failed or interrupted files remain incomplete and are not represented as verified backups. Subprocess output can contain encoded database bytes, so failure diagnostics report only the stage and private journal path.

## Final-window commands and media

The final restoration plan now invokes short direct kubectl reads, cleanup writes and release generation/verification through `scripts/deadline-command.py`. It uses the earlier of a command timeout and the original run deadline. stdout/stderr are streamed to private temporary files with a combined32MiB cap; failed output is withheld. Its child is kept unreaped while the owned process group is stopped, including residual group members after a successful leader exit. SIGTERM follows the cleanup path. Detached sessions, external SIGKILL, host shutdown and remote operations remain outside this guarantee. Darwin zombie-only group signals are handled only after a bounded check finds no live member. An uncertain cleanup never becomes a successful proof. The wrapper is for finite commands, not forwarding tunnels or daemons.

`verify-release.mjs --remote` separately bounds its remote calls and rejects an observed deadline overrun. The outer wrapper also covers local git/file stalls. Recording and deck creation use `media-deadline.cjs` with an independent watchdog and final receipt checks; copied source inventories now require that helper. A partial recording/deck remains incomplete. Human visual and claim review is still required. The explicit rehearsal mode remains available for future source reproduction, is always labelled rehearsal, and does not extend this autonomous run.
