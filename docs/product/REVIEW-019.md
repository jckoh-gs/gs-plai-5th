# 제품 검토019 — 일반 목표 폼 범위와 만료일 오류 안내 초안

상태: **채택 판단 전 검토 초안**. 현재 PRD1.10 / 제품1.3.0 / stable1.3을 유지한다. 이 검토는 코드·PRD·버전·배포를 변경하지 않는다. IDEA-008 제안v2와 ISSUE-021을 함께 검토하며, 메인이 최초1시간 관찰 구간(13:22UTC 이후)을 확인한 뒤 채택 여부를 결정한다. 사용자나 개발자의 응답을 기다리는 작업은 아니다.

## 근거와 문제 구분

[일반 입력 재현](../../artifacts/checkpoints/command-form-before/result.json)은 toleranceKw 0/10001, timeoutSeconds 0/3601, priority101이 현재 브라우저에서 nativeValid=true임을 보여준다. 실제 priority101 요청은 HTTP200으로 반환됐지만 명령 상태는 rejected, 사유는 `priority must be 0..100`이었다. 이는 서버 보호가 실패한 증거가 아니라 폼 안내와 기존 서버 범위가 다른 증거다. pageErrors는 없고, 해당 명령의 SCADA 전달은 없었다. 사용자는 서버까지 보내야 범위를 알 수 있다.

[만료일 재현](../../artifacts/checkpoints/command-expiry-before/result.json)은 validSeconds=100000000000000000000이 native validity를 통과하지만 제출 시 `Invalid time value`를 발생시킴을 보여준다. 명령 POST는0회였다. `Target`의 `new Date(Date.now()+validSeconds*1000).toISOString()`이 전송 전에 예외를 일으키며, 사용자가 수정할 수 있는 폼 오류 안내가 없다. 이는 앞의 서버범위 안내 부족과 구분되는 오류 처리 누락이다. 두 증거 모두 로컬1.3 시험이며 원격 k3s 제어 성공·실패로 확대하지 않는다.

현재 `server/control.js`는 유한한 숫자를 요구하며 toleranceKw0.01~10000, timeoutSeconds1~3600, priority0~100을 허용한다. 이 세 항목에 정수 제한은 없다. targetKw는0부터 선택 발전기 정격 합계까지이며, 순간 가용 출력이 상한은 아니다. expiresAt은 실제 유효 날짜이며 네 자리 연도의 ISO 형식이어야 한다. 현재 서버는 업무상 미래 만료기간 상한을 따로 두지 않는다.

## 채택한다면 허용할 최소 범위

일반 목표 폼의 세 항목에 서버와 동일한 min/max 및 눈에 보이는 단위·범위 안내를 둔다. `Num`의 step="any"를 유지하고, 입력값을 몰래 clamp하거나 반올림·기본값으로 대체하지 않는다. 공통 Num 전체나 다른 폼의 동작을 바꾸지 않는 Target 내부 설정만으로 충분하다.

인접한 validSeconds 처리는 Target 제출 경로 안에서만 보완한다. 제출 시 한 번 읽은 현재 시각과 입력으로 만료시각을 계산하고, 유한한 숫자 및 유효한 Date인지 확인한 뒤 ISO를 만든다. Date 자체가 유효하더라도 확장 연도(+010000 등)는 현재 서버 ISO 형식과 다르므로 호환되지 않는 형식도 제출 전에 안내한다. 변환 예외는 국소적으로 잡고 해당 필드 가까이 한국어 오류와 접근 가능한 alert/focus 안내를 제공한다. 실패 시 act 호출이나 command POST를 하지 않는다. 화면의 오류를 고친 뒤 정상 제출할 수 있어야 하며 오류가 다른 RTU의 폼에 남지 않아야 한다.

Date/서버 형식에 표현 가능한지를 검증하는 것은 업무상 만료 상한을 새로 정하는 것과 다르다. 임의의1시간·1일·1년 max를 두지 않는다. 현재0초와 소수 유효시간도 그대로 허용하여 즉시 expired가 되는 시험을 막지 않는다. 형식 검증을 통과해도 서버 시계·전달 지연에 따라 expired될 수 있으므로 클라이언트가 accepted/completed를 보장한다고 표시하지 않는다.

가용량을 넘지만 정격 이내인 target, target0, 소수 목표·오차·시간·우선순위는 유지한다. 정격 초과 목표의 서버 거절도 유지한다. 이번 제안에 가용량 기반 자동보정, 서버 계약 변경, MQTT/CLI 변경, 새로운 확인 모달이나 우회시험 모드를 넣지 않는다. 서버 검증을 클라이언트 검증으로 대체하지 않는다.

## 제안 수락 기준 — 아직 수행 결과가 아님

1. **범위와 안내:** 실제 브라우저에서 세 항목의 표시 범위·min/max·step을 확인한다. tolerance0/10001, timeout0/3601, priority−1/101을 입력하고 버튼 및 Enter 제출을 각각 시도한다. 수정할 필드가 명확히 안내되고 command POST는0회, pageerror와 unhandledrejection도0회여야 한다. native validity 속성만 읽는 것을 제출 차단 증거로 대신하지 않는다.
2. **정상 경계와 소수:** tolerance0.01/10000, timeout1/3600, priority0/100 및 정상 소수를 검증한다. 빈칸·비유한 값도 요청으로 바뀌지 않아야 한다. 입력과 실제 POST의 숫자가 같고 임의 반올림·보정이 없어야 한다. 모든 조합을 실제 장시간 명령으로 실행할 필요는 없으며, 유효성 경계 검사와 짧은 실제 정상 제어 증거를 구분한다.
3. **만료일 예외:** 재현값1e20과 유효하지만 서버 네 자리 ISO에 맞지 않는 먼 미래 값 모두, 폼 오류를 표시하며 POST0/pageerror0/unhandledrejection0이어야 한다. 정상30초와 소수 유효시간은 표현 가능한 expiresAt으로 제출되고,0초는 기존 expired 시험 경로를 유지한다. 업무상 임의 max가 없어야 한다. 유효 날짜를 현재 기본값으로 조용히 바꾸면 실패다.
4. **수정·전환·접근성:** 잘못된 값을 정상 값으로 수정한 뒤 키보드로 제출할 수 있어야 한다. 오류 문구·필드 연결·포커스가 좁은 화면에서도 확인돼야 한다. 선택 RTU 전환 후 이전 입력 오류가 다른 단지의 성공이나 실패로 표시되지 않아야 한다. 오류 상태에서 POST 수와 명령 목록 변화를 함께 확인한다.
5. **의도된 제어 의미:** 별도 소유 로컬 RTU에서 정상 목표의 accepted/executing/completed, target0이 stop과 다름, 가용량 초과이지만 정격 이내 목표가 접수되어 timed_out될 수 있음을 확인한다. 소수값이 실제 요청에서 유지되는지 비교한다. 정격 초과 요청에 대한 기존 서버 거절과 MQTT/REST 서버 검증 회귀를 보존한다. 불필요하게 기존 운영 RTU를 변경하지 않는다.
6. **출시 조건:** 구현·브라우저 인수·기존 시나리오/preview/command export·MQTT·백업/복원 게이트를 통과한 뒤 후보를 승격한다. 재현 전 증거는 남기고 후속 증거에 정확한 소스/번들·환경을 연결한다. 새 UI 검증만으로 실제 외부 VPP나 전체 목표 완료를 주장하지 않는다.

## 위험과 결정 권고

가장 큰 범위 위험은 입력 오류 안내를 제어 정책 변경으로 확장하는 것이다. 정수화, 가용량 cap, validSeconds 임의 max는 의도한 시험을 막는다. 서버 ISO 규칙과 Date 표현 가능 범위를 혼동하면 일부 매우 큰 숫자는 여전히 서버 거절까지 갈 수 있으므로 두 검증을 분리해야 한다. 브라우저 네이티브 안내는 언어·기기마다 다르므로 지속적인 범위 문구를 함께 제공하되, 모든 폼을 새 검증 체계로 바꾸는 리팩터링은 피한다. 클라이언트 검증은 편의 기능이며 보안 경계가 아니다.

권고는 첫1시간 관찰 결과가 안정적이고 남은 인수·배포·복원 및 최종 미디어 시간을 확보할 수 있을 때 제안v2를 하나의 작은 후보로 채택하는 것이다. 기존 minor 기능 추가 이력과 맞추어 **PRD1.11 / 제품1.4.0 후보**를 채택 시점에 먼저 기록하고 stable1.3을 유지하는 방안을 권한다. ISSUE-021 날짜 예외만 긴급 수정한다면 patch1.3.1이라는 별도 선택도 가능하지만, 일반 범위 안내까지 함께 넣으면서 단순 예외 수정이라고 축소 표현하지 않는다. 현재 문서는 어느 버전도 배정하거나 채택하지 않는다. 운영 관찰·동결·복원·미디어 게이트를 압박하면 이번 후보를 보류하고 ISSUE-021을 명시적으로 열린 상태로 남기는 편이 낫다.
