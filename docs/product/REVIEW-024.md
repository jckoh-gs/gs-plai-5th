# 제품 검토 024 — IDEA009 제안: REST 명령 접수 결과와 응답 유실 안내

**제안만이며 미채택·미구현이다.** 현재 stable1.4/PRD1.11, 원래 동결·종료와 미디어 조건을 유지한다. 소스와 계약을 읽었으며 실제 브라우저 재현은 독립 이슈 담당의 후속 증거를 기다린다. 이 검토는 소스 관찰을 실제 실행 PASS로 표시하지 않는다.

## 필요성과 근거

web/src.jsx의 App.act는 POST 결과 이후 GET /state까지 성공해야 결과를 반환하고 호출자가 준 성공 문구를 표시한다. Target은 HTTP200의 status를 보지 않고 “목표값을 접수했습니다”를 지정한다. server/index.js의 commands POST는 Controller.submit 결과를200으로 반환하며 server/control.js는 정상 응답으로 rejected/expired도 반환한다. 따라서0초 만료나 서버 거절을 접수 성공으로 안내할 수 있다. POST accepted 이후 상태 GET만 실패해도 현재 act는 원래 응답을 잃고 일반 실패로 처리한다. Target에는 동기 inFlight guard가 없어 연속 제출마다 다른 UUID를 만든다. 서버 중복 방지는 동일ID/동일본문에 적용되므로 서로 다른 ID 두 개는 별개 명령이며 기존 명령을 supersede할 수도 있다.

이 문제는 에뮬레이터의 핵심인 명령 수명주기 해석에 직접 영향을 준다. IDEA008의 입력 범위/날짜 검증, IDEA006의 저장 상태 다운로드와 다르다. 입력값이 유효해도 서버 접수·만료·전송 결과는 다를 수 있다. 사용자가 불확실한 응답 때문에 새 명령을 반복하는 것을 줄이는 작은 후속 후보로 채택을 권고한다.

## 최소 범위 제안

1. REST 명령 제출 경로만 별도 작은 공통 처리로 묶는다. Target의 set_target과 Dashboard의 set_limit/start/stop 및 발전기 행 start/stop에 같은 결과 의미를 적용한다. 일반 act 전체·등록·기상·시나리오 흐름은 재설계하지 않는다. 서버/DB/API 계약, 새 OSS, 자동 재전송, 전체 명령 관리자, MQTT 클라이언트 변경은 제외한다.
2. 제출 순간 RTU ID/이름, 발전기 대상, action, commandId를 고정해 접수 기록을 보여준다. accepted는 “접수됨, 실행 결과 확인 필요”, rejected는 “거절”, expired는 “만료”다. 반환된 다른 알려진 상태도 원문 상태와 의미를 유지하며 completed와 accepted를 혼동하지 않는다. 실패 상태에 성공 색상/성공 문구를 붙이지 않는다. reason은 React 텍스트로 표시하며 HTML로 해석하지 않는다. 알려지지 않은/식별자 불일치 응답은 성공으로 추정하지 않는다.
3. POST의 유효한 명령 응답은 후속 /state 갱신과 별개로 보존한다. 상태 GET 실패는 “명령 응답은 확인했으나 화면 갱신 실패”로 표시하며 accepted를 전송실패로 바꾸지 않는다. POST 응답 자체를 확인하지 못한 네트워크/파싱 실패는 “접수 여부 확인 필요”와 원래 commandId/RTU를 유지한다. 자동 재제출/새UUID 생성/성공 추정은 하지 않는다. HTTP 오류도 명령 상태와 구분해 표시한다.
4. POST를 기다리는 동안 동기 guard와 disabled/진행 문구로 연속 클릭·Enter 중복을 막는다. 탭/RTU 변경·컴포넌트 재마운트가 guard를 우회하지 않도록 제출 상태는 App 수명에 둔다. 메인과 대조한 권고 정책은 RTU별 단일 pending POST이며, 다른 RTU의 의도적 제어는 허용한다. 실행 완료까지 모든 제어를 막지 않으며, 응답 확정 후 사용자가 의도적으로 새 명령을 보내는 기존 기능은 유지한다. 여러 탭/브라우저 전체의 exactly-once는 보장하지 않는다.
5. 응답 미확정 시 기존 GET commands를 이용한 명시적 읽기 확인을 제공할 수 있다. 원래 RTU·commandId가 일치한 행만 결과로 채택한다. 목록은 최근200개이고 일부 early rejection은 저장되지 않으므로 “없음”은 미접수 증거가 아니다. 조회 실패/없음이면 미확정을 유지하고 새 명령에는 이전 결과가 불명확하다는 안내를 남긴다. 서버 재전송·자동 폴링 무한대기·세션영속 command journal은 제외한다. 선택을 바꿔도 늦은 A 응답이 B 결과로 보이면 안 된다.

## 구체적 수락 제안

- 실제 격리 서버의 accepted와0초 expired, 실제 서버 rejected 각각에서 정확한 상태·대상·ID가 표시된다. accepted가 completed라는 주장이나 rejected/expired 성공 toast가 없다.
- 실제 POST accepted 뒤 /state만 실패시키면 원래 접수 응답은 남고 갱신 경고만 추가된다. 서버 명령은1개이고 재POST가 없다.
- 서버가 명령을 저장한 뒤 응답을 차단하는 fixture에서 미확정/원래ID 유지, 읽기 확인으로 동일 저장 명령을 찾는다. POST가 서버에 도달하지 않은 fixture 및 GET 실패/목록 미포함에서는 미접수라고 단정하거나 재전송하지 않는다.
- 지연 POST 동안 빠른 클릭·Enter·탭 및 A→B→A 전환에도 단일 POST/단일ID다. 늦은 A 응답은 A 대상임을 계속 표시하며 B 상태로 오인되지 않는다. 명시적 응답 뒤 새로운 의도적 제출은 새ID로 가능하다.
- Target/상한/단지 기동·정지/개별 발전기 기동·정지에 같은 경계가 적용된다. 기존0kW·소수·가용초과·만료·범위 오류 의미와 키보드/좁은 화면을 유지한다.
- 실제 명령 이력/모델/outbox로 중복 여부를 확인한다. 버튼 disabled나 테스트 파일 존재만으로 통과하지 않는다. 기존 auth/SSE/preview/export/scenario 회귀, 정확한 후보 이미지의 k3s 확인·백업/복원 후에만 stable 승격한다.

## 위험과 결정 경계

App에 RTU별 guard를 두어 재마운트 우회를 막되 다른 RTU의 의도적 제어를 불필요하게 막지 않는다. 서버 실행 완료까지 잠그거나 긴 전역 busy로 기상/다른 기능까지 막는 것은 과도하다. 응답 유실 확인은 기존 최근 목록의 한계 때문에 완전한 복구를 보장하지 않는다. 영속 재전송 큐나 새 API를 추가하면 이번 후보 범위를 넘는다. 기본 제안은 세션 내 명령 receipt와 읽기 확인에 한정한다. POST 대기는 기존 직접 HTTP 경계와 일관된15초 등 유한 상한을 명시하고 timeout은 미확정으로 전환한다(정확한 값은 채택 계약에서 확정). pending 종료 후 의도적인 다음 명령은 허용하되 이전 미확정 receipt를 지우거나 성공으로 바꾸지 않는다. 추가 승인 모달은 필요하지 않다. receipt는 앱 메모리 범위로 새로고침 후 보존되지 않음을 안내하고 sessionStorage/영속 큐를 추가하지 않는다. 읽기 확인 버튼은 응답 유실 안내가 단순 재전송 권유로 끝나지 않도록 하는 작은 유용한 구성으로 포함을 권고한다. 임의 재시도는 허용하지 않는다.

채택할 경우에만 다음 PRD/제품 minor를 배정하고1.4 immutable checkpoint를 fallback으로 보존한다. 이번에는 PRD·package·run·runtime을 변경하지 않는다.
